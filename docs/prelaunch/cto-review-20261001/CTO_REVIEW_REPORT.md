## 3. 关键发现：最需要完成的是正式业务接线

### F-01 / P0：正式身份能识别用户，尚不等于正式V1.1业务能运行

**已看到的事实：**

`services/api/src/prelaunch/production-identity-routes.ts:25`对外能力明确返回`businessReady:false`。该文件已装配正式身份读取/初始化、受控运营身份、本人资金记录和退款申请受理等路由，但不是完整的供给发布、报名、成团和履约操作装配。

隔离业务服务`routes.ts:23-29`验证专有测试数据库，并直接创建`PersistentMockChannel`和模拟身份。`domain.ts:27-28`要求`SIMULATION_ONLY:`版本及`TEST_ONLY`政策；`:160-172`还要求`SIMULATION_APPROVED`供给及`SIMULATION_ONLY`同意证据。

因此，不是“存在一套可投入使用的正式业务，只差配置开关”。至少需要把身份、运行政策、供给确认、领域命令和客户端请求接到同一套正式应用入口。

**应保留：**隔离环境与真实业务分离、正式会话、角色版本撤销、已有纯规则和资金事实基础。

**不能采用的修法：**删除`assertSimulationPolicy()`、允许正式服务读TEST_ONLY政策、把模拟用户视为真实已同意、或简单替换一个Mock构造器。代码中还存在供给、同意、通知、审计来源等多处模拟语义。

**关闭标准建议：**正式装配路径可以在封闭测试环境中使用受控模拟传输，走完真实请求结构、正式身份适配与权限、配置读取、完整政策证据和业务命令；无真实批准时拒绝新收费。测试可以用显著隔离的合成批准材料，不能把它们变成生产授权。

证据：[E02](evidence/SOURCE_EXCERPTS.md#e02)、[E03](evidence/SOURCE_EXCERPTS.md#e03)、[E04](evidence/SOURCE_EXCERPTS.md#e04)、[E05](evidence/SOURCE_EXCERPTS.md#e05)、[E19](evidence/SOURCE_EXCERPTS.md#e19)。

### F-02 / P0：正式退款申请当前只受理，正式执行链仍未闭合

`refund-request-intake.ts:8-12`显式返回`REQUEST_INTAKE_ONLY / refundApproved:false`。`:25-26`把申请记录为`BLOCKED_POLICY`，保留原始受理时间，不创建退款指令、不改变成员、不发模拟通知或任务。

**这个受理边界本身有价值：**没有因为决策缺失丢掉用户申请或伪造退款成功。不能将其删掉或说成没有任何能力。但它不等于退款业务完成。

`refund-dispatch.ts:6-9`需要正式装配提供`authorize(tx,instructionId)`；它已实现原支付绑定、预算检查、持久化SUBMITTING、发送前权限/租约复核、UNKNOWN不重复发送等保护。L08当前报告仍明确正式authorizer由未来装配提供，正式退款执行进程/授权尚未完成。

**关闭标准建议：**

1. 受理→依据有效政策生成决定→组件退款义务/预算→批准后批次→原渠道执行→查询/回调确认→用户进度→对账，全部能通过拟发布的装配路径运行。
2. 明确authorizer的可信来源、版本、动作范围和撤销规则，不能使用空函数或`approved=true`完成装配。
3. 正式运行进程必须有任务范围、租约、心跳、故障退出、重启恢复、未知结果人工出口和审计。
4. 整条链在隔离的同代码路径用合成渠道测试；真实小额验收仍是独立QA-02。
5. 新收费许可与存量资金恢复/合法退款许可分开，不能因为新定价或某个无关RV未完成就抹掉已有义务。

证据：[E06](evidence/SOURCE_EXCERPTS.md#e06)、[E07](evidence/SOURCE_EXCERPTS.md#e07)、[E15](evidence/SOURCE_EXCERPTS.md#e15)。

### F-03 / P0：材料校验和不可变归档，不是政策生效与业务授权

`formal-policy-material.ts`核对3份正文和19项gate附件映射，返回`integrity:VALID`时依然固定`activation:NOT_ASSESSED`及`releaseAuthorized:false`。

`FORMAL_POLICY_ARCHIVE_SETUP.md`明确，`V11PolicyMaterialArchive`只有`MATERIAL_ONLY`状态，不替代`V11PolicySnapshot`，没有正式业务/用户同意/支付授权作用。

**所以提供完19项材料，也不应直接宣布ENG-03关闭。**还需要实际核验主体与签收权限、结论适用的业务分支、参数、版本范围、正式运行快照、用户看到的公开正文及同意证据，然后接到业务授权。

**关闭标准建议：**材料归档、专业/业务签收判断、运行政策、单订单同意、动作授权各自有明确来源，证明“谁、在什么版本/时间、允许哪类动作”。错误版本、撤销权限、缺材料、材料虽全但未获准、篡改公开正文时均拒绝新收费，但保留历史合法处理路径。

源码只要求19个gate各一次，并没有强制19个不同`referenceId`。资料可以按实际审查工作组织成少量专题文件，逐gate明确段落、结论和证据；**不能把“19项映射”误解为必须找19个人或写19份重复文件**。反过来，不能用一份没有逐项内容的“全部同意”文件消除所有问题。

证据：[E08](evidence/SOURCE_EXCERPTS.md#e08)、[E09](evidence/SOURCE_EXCERPTS.md#e09)、[E21](evidence/SOURCE_EXCERPTS.md#e21)。

### F-04 / P0：正式前端入口仍有旧收费口径；预览路径通过不能代替主业务路径

包内`tests/prelaunch/http-journey-recovery.test.mjs`使用`/api/prelaunch/v11`与`TEST_ONLY`；`tests/ui/prelaunch-http-dom.test.tsx`也验证预览API路径。这些测试并非无价值，但证明范围要与正式入口分开。

**关闭标准建议：**正式构建中用户进入的页面，应走同一正式API装配；覆盖F/D/总价、定价版本、候补披露、自动转正、10分钟锁位、退款档位、订单找回和本人权限。一个展示页面或另一个预览域的通过不能替代该链。

证据：[E13](evidence/SOURCE_EXCERPTS.md#e13)；包内测试文件；上述同SHA GitHub页面源码（对话中已提供连接器引用）。

### F-05 / P0：零差异容量测量不等于完整对账，也不等于资金生产就绪

当前10000笔支付+1000笔退款、44页、26741ms的记录完整存在，`differences=0`、资金字段指纹未改变也是团队记录的测量结果。

但它同时明确：

```text
scope = BILL_AND_RECORDED_FUNDS_SNAPSHOT
coverageState = INCOMPLETE
releaseAuthorized = false
paymentQueriesQueued = 10000
refundQueriesQueued = 1000
```

代码不是仅有某一次运行漏填状态；`wechat-bill-page-checkpoint.ts`的结果schema将`coverageState`限制为`INCOMPLETE`，最终写`ReconciliationBatch`也保持这个值。已实现的是可信账单获取、观察/比较及恢复组件；尚无可据此直接出具完整商户覆盖和差异结案的正式授权结论。

**另外，26.7秒不包含11000个已入队渠道查询全都执行完的证明。**后续测量需区分下载、快照、分页比较、任务生成、队列消化、差异调查和最终覆盖确认。

**关闭标准建议：**确认商户/应用/原支付范围和账期完整、必要事实与时间证据齐备、差异有真实调查/复核结案、当前候选任务恢复健康，再由独立的覆盖判定层评估。不能直接把`INCOMPLETE`常量改成`COMPLETE`来通过门禁。

32MiB/100000行是当前可见边界；它不自动意味着“小规模首发永远不能上线”，也不能无依据忽略。流式处理是否是首发硬前置，需要结合批准的负载上限、超限安全失败、资源测量和恢复策略判断；这不同于已经明确未完成的覆盖/差异闭环。

证据：[E11](evidence/SOURCE_EXCERPTS.md#e11)、[E12](evidence/SOURCE_EXCERPTS.md#e12)。

## 4. 29项阻塞如何正确处理

详细逐项表见 [GATE_RESPONSIBILITY_MATRIX.md](GATE_RESPONSIBILITY_MATRIX.md)。它保留原ID、原问题范围及未完成结论，没有自行填写金额、渠道账户或用户权益规则。

### 4.1 不再把全部工作串行为“老板填齐29项，工程才继续”

建议三条线并行：

| 线 | 负责交回什么 | 不需要做什么 |
| --- | --- | --- |
| 工程线 | ENG-01/02/03正式装配、主页面接线、权限/故障回归和差异闭环；用实际正式代码路径在隔离环境验证 | 不等待具体F价格才能做配置、校验、快照、拒绝路径；不直接开真实收费 |
| 业务/专业线 | 12个OP只处理残余、7个RV形成适用结论；专题材料逐项映射、真实责任人签收 | 不再重问已确认15项；不把AI代拟意见当实际签收 |
| 平台/运营/环境线 | 核现有小程序/商户和部署资源，安排真实餐厅、客服、真机和恢复验收 | 不重新开户、不因浏览器安全限制断言商户有问题、不在聊天传私钥 |

重要区别：工程可先完成结构、配置装载、守卫、错误路径和合成测试；真实参数未知的商业分支必须隔离，不得以测试默认值上线。已经接受的用户请求、可信实收和合法义务不能因为配置未齐就被删除或伪装成不存在。

### 4.2 真正卡住业务唯一结果的事项

优先收口OP-04/05：成员何时减少、FIFO首次生效时钟、T-24新报名类别、跨T-8但10分钟锁位未过期的收款、失效桌新客类别。这些会改变席位、退款和资格，不能由工程自行猜。

OP-03/08实际数值、OP-11批次/SLA、OP-13送达/受理、OP-14结算/翻案与账户资料，可以按各自责任专题集中填写；没有必要再次拆成逐条漫长问答。剩余OP和RV仍须按其范围处理，不能被“优先处理”这句话自动延后为非必要。

### 4.3 哪些不是靠批准就能消除

真实主体/商户既然用户已确认准备，应核现有能力而不是重新申请。审批能够允许一次特定操作，不能产生真实凭据、证明权限、替代实际测试，也不能自动装配尚不存在的业务入口。

文档签收与实际代码完成也不是互相替代：19项材料即使全齐，ENG-01/02/03仍要交正式链路的测试；工程测试全齐，也不能代RV、商户、运营和生产环境签收。

## 5. 工具限制与验收问题

### 5.1 微信平台浏览器访问

原记录是`BROWSER_SITE_SAFETY_BLOCK`，没有进入后台，也没有出现可批准的权限弹窗。它不证明商户不存在、账号异常或资质未准备。处理应由具有合法访问能力的实际管理员核验现有账号并输出脱敏能力记录，而不是让代理绕过站点安全策略。

### 5.2 开发者工具域名

当前失败是请求地址`http://127.0.0.1:3000`不符合其合法request域名校验，且接口是预览API。页面渲染与端到端成功必须分开。
